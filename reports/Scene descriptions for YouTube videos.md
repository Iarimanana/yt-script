# Give yt-script eyes without downloading video

There are three ways to get a description of what is visible in each scene of a YouTube video, and the choice depends less on which model is smartest than on two questions: **who supplies the timestamps, and who touches the video file**. **Google's Gemini API is the only major service that accepts a public YouTube URL directly**, so it can describe scenes without your tool ever downloading the video. On Flash-class models that costs roughly **$0.05–$0.45 per 15-minute video**. The catch is that the model writes its own timestamps, and developers have documented drift of **5–10 minutes over a 30-minute video** on YouTube-URL input. Every other route needs the video file: sending keyframes to Claude or OpenAI (neither accepts video), running an open model such as Qwen3.5 or Gemma 4 locally, or using a managed service such as Twelve Labs Pegasus 1.5 or AWS Bedrock Data Automation. Having the file gives you exact timestamps, because they come from your own frame extractor. But downloading conflicts with YouTube's Terms of Service, and US courts in 2026 have held at the pleading stage that YouTube's "rolling cipher" is plausibly an access control under DMCA §1201. The recommended extension adds a pluggable "describer" layer to yt-script. Its default Gemini backend never downloads the video and ties every description to time windows built from the captions yt-script already fetches. An opt-in local-file backend serves videos the user owns or has permission to use. Both feed one step that assigns caption lines to scenes by largest time overlap, and that step needs a small fix first: `transcript.py` currently discards each caption's `duration`. The research on video download and scene detection was not completed, so those parts of the design are marked as unverified throughout.

## Only Gemini watches a YouTube link; every other route needs the file

**Gemini takes a public YouTube URL as a video part of the request.** The feature is still labelled **preview** and "available at no charge", and Google warns that "pricing and rate limits are likely to change". The free tier is capped at **8 hours of YouTube video per day**, and the paid tier has no length-based limit ([Gemini API: Video understanding](https://ai.google.dev/gemini-api/docs/video-understanding)). Only public videos work. Developers have an open request to allow unlisted ones ([Google AI Developers Forum](https://discuss.ai.google.dev/t/request-allow-gemini-api-to-analyze-unlisted-youtube-videos/105083)), and a forum thread is titled "Recent YouTube Videos Inaccessible via Gemini-3-Flash-Preview API" ([Google AI Developers Forum](https://discuss.ai.google.dev/t/recent-youtube-videos-inaccessible-via-gemini-3-flash-preview-api/114076)). A model with a 1M-token context handles about **1 hour of video at default resolution or 3 hours at low resolution** ([Gemini API: Video understanding](https://ai.google.dev/gemini-api/docs/video-understanding)). On Gemini 3.x a video frame costs **70 tokens at low or medium `media_resolution`**, which Google calls "sufficient for most action recognition and description tasks". It costs **280 tokens at high**, which Google recommends for text-heavy video ([Gemini API: Media resolution](https://ai.google.dev/gemini-api/docs/media-resolution?hl=en)). The default pipeline samples **1 frame per second**, with audio at about 32 tokens per second. That figure comes from Gemini 2.x-era documentation and may be outdated ([s-anand.net](https://www.s-anand.net/blog/how-does-gemini-process-videos/)).

On 2026-09-01 Google added an **"agentic video understanding" mode**. Instead of ingesting every frame, the model calls tools such as `get_transcript`, `get_frames(start, end, fps)` and `get_audio` to choose what to watch. Google claims **up to 88% fewer tokens and 66% lower cost per query** ([NYU Shanghai RITS](https://rits.shanghai.nyu.edu/ai/gemini-agentic-video-understanding/); [MarkTechPost](https://www.marktechpost.com/2026/09/04/google-agentic-video-understanding-gemini-flash-models/)). Sources disagree on which models support it. One summary of Google's blog names Gemini 3.5 Flash-Lite ([Google blog](https://blog.google/innovation-and-ai/models-and-research/gemini-models/introducing-agentic-video-in-gemini/)); MarkTechPost names 3.7 Flash, 3.6 Flash and 3.5 Flash-Lite. An independent test reported trade-offs ([MLQ.ai](https://mlq.ai/news/google-expands-geminis-agentic-video-analysis-but-early-testing-finds-trade-offs/)). One caveat applies to all the Google facts in this report: ai.google.dev could not be fetched during research, so they come from search-engine summaries and aggregators and need checking against the live docs.

**Claude and OpenAI cannot take video, but they take many images.** Claude accepts up to **600 images per API request on 1M-context models** (100 on 200k-context models), with a **32 MB request cap**. Each image must stay at or under 2000 px per side once a request holds more than 20 images. An image costs **⌈width/28⌉ × ⌈height/28⌉ tokens**, so a 1280×720 keyframe costs 1,196 tokens. Claude "does not read image metadata", so each frame's timestamp has to be supplied as a text label ([Claude docs: Vision](https://platform.claude.com/docs/en/build-with-claude/vision)). That is a hidden strength: the timestamp comes from your extractor, not the model, so it is exact by construction. OpenAI has no video input in any API. A March 2026 feature request for native video input was **closed as "not planned"** ([openai/openai-node #1778](https://github.com/openai/openai-node/issues/1778)). Images are billed in 32×32-px patches, so a 1280×720 frame is 920 patches ([OpenAI image cost calculator](https://developers.openai.com/api/docs/guides/image-cost-calculator), via search summary).

**Managed video services need an upload, and only some write prose.** Twelve Labs **Pegasus 1.5** is the most purpose-built option. You define what a segment is and supply a JSON schema, and it returns **timestamped, structured per-segment metadata** for videos up to two hours long, with no indexing step ([Twelve Labs blog](https://www.twelvelabs.io/blog/introducing-pegasus-1-5)). It states that "the ability to upload videos from YouTube is **no longer supported**" ([Twelve Labs docs](https://docs.twelvelabs.io/docs/resources/playground/upload-and-manage-videos)). AWS Bedrock Data Automation detects shots and "chapters", writes a natural-language summary for each chapter, and needs the video in S3 ([AWS ML blog](https://aws.amazon.com/blogs/machine-learning/automate-video-insights-for-contextual-advertising-using-amazon-bedrock-data-automation/)). Amazon Nova 2 Lite samples **1 fps for videos up to 16 minutes** and is the cheapest promptable option ([AWS Nova docs](https://docs.aws.amazon.com/nova/latest/nova2-userguide/using-multimodal-models.html)). Azure Video Indexer returns scenes, shots and keyframes, but its LLM output is a whole-video summary that needs a paid account linked to Azure OpenAI ([Microsoft Learn](https://learn.microsoft.com/en-us/azure/azure-video-indexer/text-summarization-task)). Google's Video Intelligence API gives label-only shot metadata. Search extractions say it was **deprecated on 2026-09-14, with shutdown on 2027-09-14**, though one search contradicted that ([Video Intelligence deprecations](https://docs.cloud.google.com/video-intelligence/docs/deprecations)). Either way it should not be used for new work.

**Open models are now strong enough to run locally.** Qwen3.5 (Apache-2.0, released February–March 2026) runs in llama.cpp and in mlx-vlm on Apple Silicon ([QwenLM README](https://github.com/QwenLM/Qwen3.6)). Gemma 4 moved to Apache-2.0 in April 2026 ([DataNorth](https://datanorth.ai/news/google-releases-gemma-4-open-models)). The 1.3B MiniCPM-V 4.6 was added to Ollama's library in June 2026 ([OpenBMB/MiniCPM-V](https://github.com/OpenBMB/MiniCPM-V)). Two details matter for yt-script. Qwen3-VL accepts a list of **pre-extracted frames with a `sample_fps` "used to determine timestamps for each frame"**, so frames taken at scene cuts keep their real times ([QwenLM/Qwen3-VL](https://github.com/QwenLM/Qwen3-VL)). And Ollama's documented API accepts only an `images` array, not video ([Ollama vision docs](https://github.com/ollama/ollama/blob/main/docs/capabilities/vision.mdx)), whereas llama.cpp's server takes video directly, sampling at 4 fps by default and inserting a text timestamp every 5 seconds ([llama.cpp server README](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md)).

## Timestamps from your own clock beat timestamps from the model

On whole-video understanding Gemini leads clearly, but no model comes close to human performance. On **Video-MME-v2** (April 2026), Gemini-3-Pro averages 66.1% accuracy. Its score falls to **49.4** under grouped scoring, which credits a group of related questions only if every answer in the group is right. Humans score **90.7** ([Video-MME-v2](https://github.com/MME-Benchmarks/Video-MME-v2)), and GPT-5 scores **37.0** on the same grouped measure ([arXiv 2604.05015](https://arxiv.org/html/2604.05015v1)). The benchmark authors note that "models that rely more on visual frames (e.g. GPT-5 and the Qwen family) are relatively weaker", and even Gemini scores below 30 on Action & Motion ([Video-MME-v2](https://github.com/MME-Benchmarks/Video-MME-v2)). On the older, saturated Video-MME, open models have nearly caught up. Search snippets of the model card give Qwen3.5-27B **87.0 with subtitles** ([Hugging Face](https://huggingface.co/Qwen/Qwen3.5-27B)), against a reported 88.6 for Gemini 3 Pro ([BentoML](https://www.bentoml.com/blog/multimodal-ai-a-guide-to-open-source-vision-language-models)). Treat vendor numbers as upper bounds: one user who ran Qwen3.5-9B through Hugging Face transformers measured **69.81 against the official 78.4** ([QwenLM issue #86](https://github.com/QwenLM/Qwen3.6/issues/86)). These benchmarks measure question answering, not timestamped captioning. A per-scene pipeline mostly needs frame-level perception and OCR, where the gap between the top models is narrower.

**Timestamps are where model-driven approaches fail.** In a python-genai issue, a developer passing YouTube URLs to Gemini 2.5 saw timestamps drift **5–10 minutes over a 30-minute video**, and the output stopped at about minute 17. The issue was closed as "not planned". The same reporter found that **downloading and uploading the file instead gave accurate timestamps** ([python-genai #1359](https://github.com/googleapis/python-genai/issues/1359)). Gemini 3 Flash and 3.1 Pro show *progressive* drift in audio transcription: an 11:49 clip was mapped onto 0:00–9:14, a clock running about 22% fast ([Google AI Developers Forum](https://discuss.ai.google.dev/t/bug-gemini-3-flash-and-3-1-pro-progressive-timestamp-drift-in-audio-transcription/129501)). In agentic mode, one tester saw a recurring scene labelled 10:41 when it actually appeared at 10:50 ([Han Qi, Medium](https://hanqi01.medium.com/unlocking-geminis-agentic-video-mode-schema-design-timestamp-drift-and-jay-chou-s-secret-215715dfcdb7)). Research on dense video captioning (segmenting a video and captioning each segment in one pass) agrees. The TA-Prompting paper (WACV 2026) states that "existing VideoLLMs remain challenging in identifying precise event boundaries in untrimmed videos" ([arXiv 2601.02908](https://arxiv.org/html/2601.02908v1)). Zero-shot TRACE reaches only **2.2 SODA_c on YouCook2** ([TRACE](https://github.com/gyxxyg/TRACE)), against **7.7 SODA** for the fine-tuned Vid2Seq ([Vid2Seq](https://github.com/google-research/scenic/tree/main/scenic/projects/vid2seq)). Baidu's CodecCap work found that "captions directly generated by strong VLMs still miss many visual details" ([CodecCap](https://www.emergentmind.com/papers/2605.26967)).

The lesson is to **never let the model both segment and timestamp the video**. Working systems split those jobs. NVIDIA's Video Search & Summarization blueprint caps the chunk size and samples a few frames per chunk (8 of 900 in a 30-second example) before captioning, then aggregates the captions ([NVIDIA VSS docs](https://docs.nvidia.com/vss/2.4.1/content/architecture.html)). Microsoft's Azure sample splits video into 16-second segments and sends each segment's frames together with its Whisper transcript ([Azure-Samples](https://github.com/Azure-Samples/video-analysis-with-aoai)). Several open-source projects build "timeline atoms" ("one shot, its timecodes, what is said and what is seen") from PySceneDetect cuts: `video_editor_agent`, `feedanalyser` and `cinematlas` ([video_editor_agent](https://github.com/OdakK/video_editor_agent); [feedanalyser](https://github.com/Sriikaran/feedanalyser); [cinematlas](https://pypi.org/project/cinematlas/0.16.3/)). The frames-based approach has its own blind spot. Sampled frames "lose audio, temporal context, and motion" ([Primate Intelligence](https://primateintelligence.ai/blog/primate-vision-vs-openai), a vendor with a competing product), so actions that happen between keyframes go unseen.

Two findings shape the prompt. Claude's documentation warns of hallucination on low-quality or small images and of only approximate counting ([Claude docs: Vision](https://platform.claude.com/docs/en/build-with-claude/vision)). Reading on-screen text needs higher resolution, which is why Google recommends high `media_resolution` for text-heavy video ([Gemini: Media resolution](https://ai.google.dev/gemini-api/docs/media-resolution?hl=en)). Audio-description research adds two cautions. LLM descriptions "are often too long", and giving the model only the dialogue for the current scene works better than the whole script ([NarrAD, WACV 2025](https://openaccess.thecvf.com/content/WACV2025/papers/Park_NarrAD_Automatic_Generation_of_Audio_Descriptions_for_Movies_with_Rich_WACV_2025_paper.pdf)). The prompt should therefore include only each scene's own caption lines, labelled as audio context, and tell the model to describe only what is visible. No study was found that measures how much this reduces hallucination.

## Scene cutting and keyframe selection are the least-verified layer

The planned research on video download and on shot-detection tools was stopped before completion, so this layer of the design rests on what the other notes mention in passing. What they do establish is limited. In **PySceneDetect**, ContentDetector's default threshold is **27.0**, and one source recommends a minimum scene length of about **0.6 s**. Good parameters vary by content type, and talking-head video produces few detections ([PySceneDetect docs](https://www.scenedetect.com/docs/latest/)). The pipelines that use PySceneDetect take one middle keyframe per shot and cap scenes at 30 seconds (cinematlas), or use AdaptiveDetector with a validator that checks the timeline is ordered and gapless (feedanalyser). The most detailed public design is `claude-real-video`. It combines **ffmpeg scene-change detection** (default threshold 0.30) with a 1-fps density floor, and drops frames too similar to the last four it kept (8% of pixels must change). It added an "action channel" because that comparison is blind to subjects covering less than 1% of the frame. A `--text-anchors` mode forces a frame at each subtitle timestamp for lectures and talking heads. On a 3-minute 640×360 video, 170 frames used about **52k tokens**, or about **25k when capped at 80 frames**. Its README argues that fixed 1-fps sampling, Gemini's approach, over-samples static content and under-samples fast cuts ([claude-real-video](https://github.com/HUANGCHIHHUNGLeo/claude-real-video)). Managed shot detection also exists: AWS Rekognition charges **$0.05/min** for shot detection ([Rekognition pricing](https://aws.amazon.com/rekognition/pricing/)), and Azure Video Indexer's Basic preset includes scene, shot and keyframe detection ([Azure pricing](https://azure.microsoft.com/en-us/pricing/details/video-indexer/)).

On downloading, the notes establish only that the path is operationally fragile. Since about September 2025, **yt-dlp needs an external JavaScript runtime** (Deno is recommended) to download from YouTube ([GIGAZINE](https://gigazine.net/gsc_news/en/20250925-yt-dlp-deno-javascript-runtime)). Some YouTube clients need PO tokens, and YouTube is forcing SABR streaming on some of them ([yt-dlp #15043](https://github.com/yt-dlp/yt-dlp/issues/15043); [yt-dlp #15897](https://github.com/yt-dlp/yt-dlp/issues/15897)). YouTube also blocks most cloud-provider IPs from its caption endpoint ([youtube-transcript-api](https://github.com/jdepoix/youtube-transcript-api)), and yt-script's README already warns users about this. Everything in the next table was **not researched**. Treat these as open questions, not findings.

| Topic | Status | What remains unknown |
|---|---|---|
| TransNetV2 (neural shot detector) | **Unverified gap**: not covered by any note | Accuracy against PySceneDetect on YouTube content, speed, packaging |
| ffmpeg `select='gt(scene,…)'` filter | **Unverified gap**: known only through claude-real-video's 0.30 default | Score semantics, threshold guidance, speed |
| PySceneDetect detectors in depth | **Partially verified**: default threshold and minimum-length advice only | Adaptive vs Content detector accuracy, Python API details, CPU cost per minute |
| Keyframe selection strategies | **Partially verified**: project practices only (middle frame, dedup window, 8 frames per 30 s) | No comparative evaluation of how frame choice affects description quality |
| YouTube storyboards (sprite thumbnails) | **Unverified gap**: not covered | Whether they are usable as a no-download low-resolution frame source, and their ToS status |
| YouTube creator chapters | **Unverified gap**: not covered | Whether chapter markers could serve as coarse scene boundaries |
| yt-dlp download mechanics | **Unverified gap**: only the JS-runtime, PO-token and SABR issues above | Format and resolution selection, partial-section downloads, reliability in 2026 |
| Gemini clipping (`videoMetadata` start/end offsets, custom fps) | **Unverified gap**: field names and limits could not be confirmed | Whether clipping works on YouTube URLs, and whether clipped requests are billed only for the clip |

## Downloading, not describing, is where the legal risk lives

YouTube's Terms of Service say users may not "access, reproduce, **download**, distribute… any part of the Service or any Content" except "as expressly authorized by the Service" or with prior written permission. They also forbid access "using any automated means (such as robots, botnets or scrapers)" except for public search engines or with permission ([YouTube Terms of Service](https://www.youtube.com/static?template=terms)). A third-party tracker logged 2026 edits to the Terms that it describes as administrative, with no change to these clauses ([ConductAtlas](https://conductatlas.com/change/2026-04-19-youtube-youtube-terms-of-service-543/)). The YouTube API Developer Policies separately bar API clients from downloading, caching or storing audiovisual content without approval ([YouTube API Developer Policies](https://developers.google.com/youtube/terms/developer-policies)). yt-script already uses automated access today. `youtube-transcript-api` calls "an undocumented part of the YouTube API" used by the web client ([youtube-transcript-api](https://github.com/jdepoix/youtube-transcript-api)), and yt-dlp reads the channel listings. Adding a video download would go further, breaking the Terms' explicit download prohibition and adding anti-circumvention exposure.

That exposure grew in 2026. In **Cordova v. Huneault** (a California federal court, February 2026), the judge found it adequately pled that YouTube's "rolling-cipher technology" effectively controls access under §1201(a), and noted that circumvention liability is separate from fair use ([TechSpot](https://www.techspot.com/news/111250-youtube-reaction-videos-could-face-lawsuits-over-ripped.html)). A court denied Snap's motion to dismiss a creators' DMCA scraping claim ([Sigma Law Group](https://sigmalawgroup.com/blog/2026-08-26-snap-dmca-scraping/)). The SDNY let the labels' circumvention claim against Udio proceed on 2026-04-15 ([Sher Tremonte](https://shertremonte.com/2026/05/11/client-alert-for-ai-companies-how-you-get-your-training-data-matters-sdny-allows-dmca-claim-to-proceed-against-ai-music-generator-udio/)). Apple's motion arguing that public videos are not access-controlled was still pending ([AppleInsider](https://appleinsider.com/articles/26/07/03/apple-says-public-youtube-videos-can-be-used-in-ai-lawsuit-defense)). In Germany, the Hamburg Higher Regional Court held in 2024 that youtube-dl bypasses YouTube's technical protection ([TorrentFreak](https://torrentfreak.com/court-rejects-appeal-of-youtube-dl-hosting-provider-uberspace-241127-1/)), and in **October 2025 the Federal Court of Justice declined to hear the appeal**, ending the case ([GFF](https://freiheitsrechte.org/themen/starke-grundrechte-fuer-eine-lebendige-demokratie/uberspace-youtube-dl)). All the US rulings came at the motion-to-dismiss stage, and all target commercial bulk scrapers or republishers. **No case was found against an individual downloading for private analysis.** So the risk to a personal CLI user is real in principle but untested.

Two things that look relevant are not. First, YouTube's December 2024 third-party AI-training setting only lets creators opt in to training. YouTube says it "does not change our Terms of Service" and that unauthorized scraping "remains prohibited" ([YouTube Help](https://support.google.com/youtube/answer/15509945?hl=en)). Running inference to write descriptions is not training, so the setting neither helps nor hurts. Second, Twelve Labs dropping YouTube ingestion shows vendors pulling away from that path ([Twelve Labs docs](https://docs.twelvelabs.io/docs/resources/playground/upload-and-manage-videos)). Gemini's URL feature is the only route on which the user's machine never fetches the video, because Google, which owns YouTube, does the fetching. That arguably fits the "expressly authorized by the Service" exception better than any download. **No source was found confirming that it settles the ToS question**, and no source was found on whether sending frames to a third-party AI provider is fair use. For anything published, original prose describing what is on screen is more transformative than a verbatim transcript under the general fair-use factors ([University of Delaware](https://www.udel.edu/edtech/youtube/modules/09-copyright.html)). That is reasoning from principles, not from a ruling on this use. None of this is legal advice.

## Recommended architecture: two describers on one caption-anchored timeline

### Fix the timeline yt-script already has

The captions are the tool's key asset. They are an exact, authoritative clock, and they give each scene its own local context. Today `fetch_transcript` builds `Line(snippet.start, snippet.text)` and discards `snippet.duration`, even though `youtube-transcript-api` returns `text`, `start` and `duration` for every snippet ([youtube-transcript-api](https://github.com/jdepoix/youtube-transcript-api)). `Paragraph` likewise records only `start`. The first change is to add `duration` to `Line` and `end` to `Paragraph`. Because auto-captions roll and overlap, each line's end should be clipped to the next line's start. This change is backwards-compatible: `format_script` and the current JSON keys stay the same, and `render_json` gains an `end` field.

### Put two describers behind one interface

| New module | Responsibility |
|---|---|
| `yt_script/scenes.py` | The `Scene` dataclass (index, start, end, `timing_source`, visual fields, confidence). Also `align_transcript(scenes, lines)` and `validate_timeline()`, which checks that scenes are ordered, inside the video and non-overlapping, and clamps or flags them. |
| `yt_script/describe/__init__.py` | A `Describer` protocol, `describe(video, windows, transcript) -> list[Scene]`, and a registry that looks backends up by name. |
| `yt_script/describe/gemini.py` | Default backend. Sends the YouTube URL with caption windows; no download. |
| `yt_script/describe/frames.py` | Opt-in backend. Takes a local file, detects shots, picks keyframes and sends them to a vision model. |
| `yt_script/describe/vlm.py` | Image-model adapters: Claude (Messages and Batch), OpenAI, and Ollama or llama.cpp for local models. |
| `yt_script/cache.py` | An on-disk JSON cache keyed by (video id, window or scene, model, prompt version, detail level), so reruns cost nothing. |

New CLI flags are `--scenes` (turns visual descriptions on), `--describer {gemini,claude,openai,ollama}` (default `gemini`), `--model`, `--video-file PATH` (required by every non-Gemini describer and valid only when a single video is selected), `--window SECONDS` (default 60), `--detail {low,high}`, `--max-cost USD`, and two new values for `--format`: `md` and `vtt`. SDKs go in optional extras (`yt-script[gemini]`, `[claude]`, `[local]`), so the base install keeps today's three dependencies. The tests should follow the existing offline pattern, using recorded model JSON as fixtures and unit tests for alignment and validation.

```
yt-script @SomeChannel --title "…" --scenes --timestamps
yt-script @SomeChannel --title "…" --scenes --describer claude --video-file ./my-upload.mp4 --format json
```

### Default backend: Gemini over caption windows, with no download

This backend is built so that Gemini never decides the coarse timeline. It merges consecutive transcript paragraphs into windows of at most `--window` seconds and adds a tail window after the last caption, since visuals often continue after speech ends. Each window is sent as its own request. The request carries the YouTube URL, clip offsets for that window, the window's caption lines labelled `AUDIO CONTEXT — do not describe`, and a JSON response schema. Gemini lists the shots inside the window with times **relative to the window start**. The code then adds the offset, clamps each time to the window, enforces ordering, and merges shots that straddle a window boundary. Every scene therefore lands in the right window, and only the within-window sub-shot times are model-generated. The 22% clock error reported for audio transcription would mean at most about ±13 seconds within a 60-second window. That bound is an extrapolation from a different task, not a measurement.

The default is low `media_resolution` (70 tokens per frame). A window is re-run at high resolution only when the model reports substantial `on_screen_text`. Gemini's Batch mode, about 50% off ([devtk.ai](https://devtk.ai/en/models/gemini-3-5-flash/)), suits `--latest N` runs. **The design depends on one unverified feature**: that clip offsets work on YouTube URLs and are billed only for the clip. Before writing the code, check this with a single billed request. If clipping does not work, the fallback is one whole-video request that lists the caption windows by ID and text and asks for one description per ID. The model then never writes a timestamp, and Gemini's audio processing lets it match each window by its speech. This fallback is an inference that has not been tested. Because the backend only works on public videos, Gemini's refusal should be passed to the user as a `YtScriptError`.

### Opt-in backend: local file, shot detection, keyframes

For a video the user owns or has permission to use, `--video-file` supplies the pixels and YouTube supplies the captions as it does today. The pipeline runs PySceneDetect (ContentDetector or AdaptiveDetector, minimum scene about 0.6 s) or ffmpeg's scene filter. It merges shots shorter than the minimum, splits scenes longer than 30 seconds, and forces a frame at caption timestamps on long talking-head stretches, borrowing claude-real-video's `--text-anchors` idea. Detector choice and thresholds are **unverified for this content** and should be tuned on the target channel. Each scene gets one to three keyframes no wider than 1280 px (1,196 Claude tokens each), deduplicated against recently kept frames. Each frame is labelled in text, for example `Scene 7 · frame 2 · 3:52`, and the frames go in batches of 20–60 per request together with each scene's caption lines. Timestamps come from the detector, so they are **exact by construction**. The default model is Claude Haiku 4.5 through the Batch API (about $0.05 per 60 frames). Sonnet 5 is the higher-quality setting (about $0.11 batched). A local Gemma 4, MiniCPM-V 4.6 or Qwen3.5 model through Ollama's `images` array costs no API fees, but expect less consistent output than Gemini, as the Video-MME-v2 results suggest. An optional text-only second pass, as in NVIDIA VSS and video-analyzer ([video-analyzer](https://github.com/byjlw/video-analyzer)), merges neighbouring scenes whose descriptions are nearly identical.

### Align, render and control cost the same way for both backends

Alignment gives each clipped caption line to the scene it overlaps most. YouTube captions have no word-level timing, so a line that crosses a cut stays whole. Splitting it exactly would need word-level ASR such as WhisperX, which this design leaves out. Each scene record looks like this:

```json
{"index": 7, "start": 221.0, "end": 252.4, "timing_source": "captions|shot-detector|model",
 "visual": {"shot_type": "close-up", "setting": "…", "people": [{"description": "…", "action": "…"}],
            "objects": ["…"], "on_screen_text": "…", "camera_motion": "static", "summary": "…"},
 "confidence": 0.8, "transcript": {"first_line": 88, "last_line": 95, "text": "…"}}
```

The `timing_source` field tells readers which times they can trust. Text output puts a `[3:41–4:12] SEEN:` line before the matching `SAID:` paragraph. `--format vtt` writes a WebVTT descriptions track, the W3C-standard way to ship text descriptions timed to the video ([W3C H96](https://www.w3.org/WAI/WCAG22/Techniques/html/H96.html)). Before any paid call, `--max-cost` estimates the spend and stops if it would be exceeded. For Gemini the estimate is duration × (70 + 32) tokens at low resolution, where the audio rate is assumed from older docs. For Claude it is frames × ⌈w/28⌉ × ⌈h/28⌉.

| Configuration | Est. cost per 15 min | Timestamp accuracy | Description strength | Downloads |
|---|---|---|---|---|
| Gemini URL, 60 s caption windows, low res (default) | ~$0.05–$0.17 | Window exact; sub-shots model-set | Best whole-video understanding on benchmarks; weaker OCR; can miss sub-second shots at 1 fps | No |
| Same at high res | ~$0.15–$0.45 | Same | Better on-screen text | No |
| Local file + Claude Haiku 4.5, batched | ~$0.05 | Exact (detector) | Good per frame; misses motion between keyframes | User-supplied file |
| Local file + Claude Sonnet 5, batched | ~$0.11 | Exact | Higher detail | User-supplied file |
| Local file + Qwen3.5-9B or Gemma 4 | $0 API, local GPU time | Exact | Close to frontier on Video-MME v1; less consistent | User-supplied file |

### Build the legal guardrails into the design

The default path keeps the README's current promise that "no video is downloaded". The tool should ship **no built-in downloader**. `--video-file` takes files the user already has rights to, and if a download command is ever added, it should be a separate command that requires explicit opt-in and shows a warning. Caches stay local, and frames are never written to output. The README's "only use transcripts in ways the video's creator and YouTube's terms allow" line should also cover visual descriptions. It should add that descriptions are safer to publish than verbatim transcripts, and that users should check their AI provider's data-retention terms, which this research did not examine.

## Conclusion

The research turned up something a transcript tool does not expect: its captions are what make a no-download design work. They provide an authoritative clock and scene-local context, which keeps Gemini's weakest property, timestamp drift, confined to a single caption window. A design that ignores the captions has to choose between trusting the model's clock and downloading the video. The decisive factor turns out to be legal posture rather than model quality. For a per-scene document, a scene stamped at the wrong minute is a more visible defect than a slightly less detailed description, and the legal risk sits entirely in the download step.

Three checks should come before code, because the architecture depends on them. First, send one billed Gemini request to confirm that clip offsets work on YouTube URLs and are billed only for the clip. Second, run a small bake-off of PySceneDetect, ffmpeg's scene filter and TransNetV2 on the target channel's own videos, since talking-head and heavily edited content behave very differently. Third, check current Gemini model names and prices on Google's official page. Putting Gemini behind the `Describer` interface means that if the preview feature changes terms or disappears, replacing it touches one module rather than the whole tool.
